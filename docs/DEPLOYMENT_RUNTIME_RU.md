# Серверный runtime TG Sender 2.0

Этот документ описывает подготовленный контейнер. Наличие Dockerfile и успешная локальная сборка JavaScript сами по себе не подтверждают сборку образа, развёртывание, доступность сервера или доставку сообщений. Конкретный хост, домен, PostgreSQL и способ хранения внешних резервных копий проверяются отдельно при публикации.

## Состав и запуск

В одном контейнере запускаются существующие API и фоновый worker. Перед ними выполняются скомпилированные миграции из `dist/migrate.js`; `tsx` на сервере не нужен. PostgreSQL находится вне контейнера. Supervisor перезапускает упавший дочерний процесс, `tini` передаёт завершение процессу supervisor и убирает осиротевшие процессы.

База образа — официальный `node:24-trixie-slim`. Клиенты `pg_dump` и `pg_restore` версии 17 устанавливаются из репозитория Debian. Сборка использует `pnpm@10.4.1` и `--frozen-lockfile`; финальный образ содержит только production-зависимости. Приложение работает от пользователя `node` (UID/GID 1000), не от root. Для воспроизводимого релиза следует сохранить digest проверенного образа и разворачивать именно его.

Источники: [официальные варианты Node.js Docker](https://github.com/nodejs/docker-node/blob/main/versions.json), [PostgreSQL 17 client в Debian Trixie](https://packages.debian.org/stable/postgresql-client-17).

```sh
docker build --pull --tag tg-sender:release .
```

При запуске оркестратор передаёт секреты из своего secret manager. Секреты нельзя передавать через build arguments или включать в образ. `.dockerignore` разрешает только необходимые исходники и конфигурацию сборки; `.env`, `.runtime`, Git, резервные копии, внутренние документы и тестовые данные исключены. Не копировать локальную `.env` в публичные инструкции, журналы или настройки сборки.

| Параметр runtime                        | Требование                                                                                              |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `APP_ORIGIN`                            | Точный публичный HTTPS origin, например `https://sender.example.com`; без пути и завершающих параметров |
| `DATABASE_URL`                          | Прямое подключение к выделенному PostgreSQL, с доступом к миграциям и собственным таблицам              |
| `DATABASE_SSL`                          | По умолчанию `verify-full`; удалённая база всегда проверяет TLS-сертификат                              |
| `DATABASE_CA`                           | PEM доверенного CA, если сертификат провайдера требует собственного центра сертификации                 |
| `OWNER_OPEN_ID`                         | Постоянный идентификатор владельца; сохранить при переносе существующей базы                            |
| `OWNER_PASSWORD_HASH`                   | Существующий scrypt hash пароля, не открытый пароль                                                     |
| `SESSION_SECRET`                        | Секрет подписи сессий                                                                                   |
| `ENCRYPTION_KEY`                        | 32 байта в base64; при переносе существующей базы сохранить исходный ключ шифрования                    |
| `BACKUP_KEY_BASE64`                     | Отдельные 32 байта в base64, отличающиеся от `ENCRYPTION_KEY`                                           |
| `TELEGRAM_WEBHOOK_SECRET`               | Секрет проверки webhook; хранить независимо от исходников                                               |
| `HOST` / `PORT`                         | По умолчанию `0.0.0.0` / `3037`; порт должен совпадать с настройкой ingress                             |
| `LIVE_SEND_ENABLED`                     | По умолчанию `false`; сухой прогон не отправляет сообщения                                              |
| `TELEGRAM_API_ID` / `TELEGRAM_API_HASH` | Нужны только для подключения личного Telegram-аккаунта                                                  |

Требуется прямое PostgreSQL-соединение либо пул в session mode. Transaction pooling несовместим с используемыми долгоживущими session advisory locks. PostgreSQL 17 client умеет читать совместимые более старые серверы; перенос на PostgreSQL новее 17 требует обновить клиент резервного копирования и повторить проверку восстановления.

Секреты существующей локальной базы сохраняются только при целенаправленном переносе этой базы. Создание новой пустой базы означает отдельную установку. Мигратор не принимает неизвестную старую схему автоматически: `ADOPT_LEGACY_SCHEMA=true` предназначен только для ранее проверенной схемы с подготовленным бэкапом.

## Проверка доступности

Workflow `.github/workflows/container.yml` собирает `linux/amd64` на GitHub Actions и запускает образ вместе с одноразовым PostgreSQL 17. Для теста создаются случайные синтетические секреты; доступ к registry и production secrets отсутствует. Проверяются готовность worker, HTML-интерфейс, вход, защищённая cookie, отсутствие root и ежедневный зашифрованный бэкап. PostgreSQL и приложение разделяют только тестовый network namespace, поэтому соединение с базой остаётся loopback. Образ никуда не публикуется. Результатом проверки считается успешный завершённый запуск workflow для конкретного коммита, а не наличие файла workflow.

Единственный сторонний action — [официальный `actions/checkout v7.0.1`](https://github.com/actions/checkout/releases/tag/v7.0.1), закреплённый на commit `3d3c42e5aac5ba805825da76410c181273ba90b1`. Токен имеет только `contents: read` и не сохраняется в Git. Docker CLI используется напрямую на `ubuntu-24.04`; остальные actions и их дополнительные токены не нужны. Теги `node:24-trixie-slim` и `postgres:17` обновляются внутри выбранных major-версий; production следует закреплять по digest уже проверенного образа.

`GET /healthz` подтверждает, что API отвечает. `GET /readyz` возвращает HTTP 200 только при доступной базе и свежем успешном цикле worker; иначе HTTP 503. Docker HEALTHCHECK использует `/readyz`, даёт 90 секунд на запуск и три попытки с интервалом 30 секунд. Сам Docker HEALTHCHECK не перезапускает нездоровый контейнер: restart policy и реакция на readiness настраиваются у хоста отдельно.

Для первой публикации достаточно одной постоянно работающей реплики. Worker нужен и без открытой страницы: он выполняет расписания, обработку очереди и обслуживание. Платформа, которая полностью останавливает контейнер между HTTP-запросами, не обеспечивает выполнение расписаний. Простой Cloudflare Tunnel к компьютеру также не обеспечивает доступность после выключения компьютера.

Прокси должен сохранять HTTPS-доступ и передавать API/webhook без кэширования. Публичный origin обязан совпадать с `APP_ORIGIN`, иначе защищённые действия отклоняются. Проверять вход, сохранение черновика, сухую кампанию, её отчёт, readiness и восстановление после перезапуска через фактический публичный URL. HTTP 200 домашней страницы не заменяет эту проверку.

При завершении дать не менее 60 секунд на остановку API, worker и текущего обслуживания. При смене версии не запускать независимо старую и новую отправку без проверки очереди и migration compatibility. При откате использовать предыдущий проверенный образ; откат образа сам по себе не откатывает схему базы.

## Постоянные данные и резервные копии

Источником истины служит внешний PostgreSQL. Встроенный ежедневный бэкап создаёт зашифрованные архивы в `/app/.runtime/backups`. Файловая система контейнера может исчезнуть при пересоздании: такие архивы нельзя считать внешней резервной копией.

Для постоянного хоста подключить защищённый persistent volume в `/app/.runtime` с владельцем UID/GID 1000 и обеспечить копирование зашифрованных архивов в отдельное хранилище. Для платформы без постоянного диска требуется отдельная автоматическая выгрузка архивов или независимая резервная копия PostgreSQL у провайдера. В текущем контейнере автоматическая выгрузка в R2/S3 ещё не реализована. Локальный успешный бэкап не подтверждает сохранность вне хоста.

`ENCRYPTION_KEY` и `BACKUP_KEY_BASE64` должны иметь отдельную защищённую резервную копию: без первого не расшифровать Telegram credentials, без второго не восстановить архив. Проверку восстановления проводить в отдельной временной базе. Основную рабочую базу не перезаписывать.

## Критерии готовности конкретного размещения

1. Образ действительно собран и запускается на целевой архитектуре без root; версия и digest зафиксированы.
2. Миграции прошли в выбранной базе по проверяемому TLS; секреты отсутствуют в образе и журналах.
3. Публичный HTTPS URL открывается, владелец входит, сухая кампания проходит до отчёта; реальные отправки остаются выключенными до отдельного пилота.
4. Worker продолжает работать без браузера и после перезапуска контейнера, очередь и черновики сохраняются.
5. Проверены off-host бэкап, доступ к ключам и восстановление в отдельную базу.
6. У хоста есть restart policy, наблюдение за `/readyz` и отсутствие зависимости от домашнего компьютера.
