# TG Sender 2 — эксплуатация и восстановление

## Подключение старой базы

Миграции не запускаются над неизвестной старой схемой автоматически: нужен резервный снимок, проверка структуры и явный `ADOPT_LEGACY_SCHEMA=true`. Миграция 012 переводит прежние даты без часового пояса в абсолютные даты, используя `TimeZone` соединения миграции. Перед переносом старого сервера проверьте его исходный часовой пояс и способ записи каждого поля: старые поля, записанные приложением как UTC без пояса, требуют отдельного согласованного преобразования. Локальная проверка не доказывает корректность неизвестных исторических данных.

Если старые Telegram-секреты лежат открытым текстом, после резервирования базы и ключа, миграций схемы и остановки API/worker выполните `pnpm exec tsx scripts/migrate-secrets.ts`. Команда требует `LIVE_SEND_ENABLED=false` и отсутствие свежего heartbeat worker, проверяет уже зашифрованные значения и атомарно шифрует прежние. Повреждённое значение отменяет транзакцию. Старую базу не используйте для первого испытания.

## Ежедневные резервные копии

Worker запускает обслуживание в отдельной фоновой задаче. PostgreSQL хранит время следующей копии и результат; блокировка PostgreSQL не позволяет двум worker одновременно создавать одну плановую копию. После успеха следующая копия назначается через 24 часа. После ошибки — повтор через час с понятным кодом в защищённом разделе состояния.

Архив содержит только базу из `DATABASE_URL`, включая зашифрованные Telegram credentials. `pg_dump` читает согласованный снимок. Числа строк и контрольные суммы применённых миграций записаны в тот же зашифрованный архив для проверки восстановления.

Архивы находятся в `.runtime/backups` внутри этого проекта. Папка закрывается правами текущего пользователя; Windows также оставляет доступ SYSTEM. Шифрование — AES-256-GCM с новым nonce для каждого файла, защищающим данные и целостность. Незашифрованный дамп на диск не записывается. Сначала создаётся `.partial`, затем после успешного завершения и синхронизации файл атомарно переименовывается в `.tgbak`.

Нужны:

- `BACKUP_KEY_BASE64` — отдельные случайные 32 байта в Base64. Ключ не должен совпадать с `ENCRYPTION_KEY`.
- `PG_BIN` — папка с совместимыми `pg_dump` и `pg_restore`. Windows по умолчанию: `C:/Program Files/PostgreSQL/17/bin`; на других системах используются утилиты из PATH.
- Рабочий PostgreSQL и настроенный TLS. `DATABASE_SSL=disable` разрешён только для loopback.
- `BACKUP_TIMEOUT_SECONDS` необязателен: общий предел работы утилиты по умолчанию 900 секунд, допустимо 60–7200. Ожидание блокировки таблицы для `pg_dump` ограничено 30 секундами.

Отсутствующий или неправильный ключ останавливает резервное копирование. Пароли передаются PostgreSQL-утилитам только через окружение дочернего процесса, не через аргументы команд и не через логи.

Ключи, приватный `.env`, пароль владельца и пароль БД хранятся отдельно от дампа. Для восстановления Telegram credentials нужны и `BACKUP_KEY_BASE64`, и прежний `ENCRYPTION_KEY`. Сохраните их в отдельном защищённом хранилище. Потеря ключей делает соответствующие данные невосстановимыми. Автоматической загрузки в облако нет; копии на том же диске защищают от ошибки данных, но не от потери самого диска.

Принудительная копия:

```powershell
pnpm exec tsx scripts/backup.ts
```

## Проверка восстановления

```powershell
pnpm exec tsx scripts/restore-rehearsal.ts
```

Можно вторым аргументом передать только имя существующего `.tgbak` из `.runtime/backups`. Скрипт сначала проверяет аутентичность всего архива, затем создаёт **новую** временную базу с именем `tg_sender_rehearsal_<случайное значение>`. Нужны права CREATE DATABASE. Приложение и Telegram worker к этой базе не подключаются. После `pg_restore` скрипт сверяет таблицы, количество строк и контрольные суммы миграций, затем удаляет только созданную им временную базу. Рабочая база не перезаписывается.

Успех подтверждает JSON с `verified: true`, числом проверенных таблиц/миграций и `temporaryDatabaseRemoved: true`. Успешный `pg_dump` сам по себе ещё не подтверждает возможность восстановления — нужна эта проверка.

Если процесс принудительно завершён, временная база может остаться. Перед её удалением вручную проверьте точное имя, отсутствие активной проверки и то, что имя начинается с `tg_sender_rehearsal_`. Никогда не удаляйте рабочую базу. Незавершённые `.partial` также можно удалить только после проверки, что резервное копирование сейчас не выполняется.

## Хранение и инциденты

Автоматического удаления архивов сейчас нет. Контролируйте свободное место. Удаляйте старые копии вручную после успешной проверки более новой; храните необходимые дневные и недельные точки восстановления согласно срокам хранения данных вашей организации. Не удаляйте единственную проверенную копию.

При проблемах смотрите `maintenance_jobs`: `status`, `last_success_at`, `next_run_at`, `last_error`, `last_rehearsal_at`. Ошибки содержат коды, без credentials и содержимого сообщений. Не отправляйте `.env`, ключи и дампы в чат, issue или Git.

После реального аварийного восстановления сохраняйте `LIVE_SEND_ENABLED=false`, проверяйте результаты очереди и sender controls. Доставки, оставшиеся `inflight` после сбоя, должны перейти в `unknown` и не повторяться автоматически. Восстановление работоспособности не даёт разрешения повторно отправлять сообщения с неизвестным исходом.
