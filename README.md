# TG Sender 2.0

Кандидат версии **2.0.0**: локальный сервис управляемых Telegram-рассылок через Bot API и MTProto. Основное правило — один раз настроить аудиторию и сценарий, затем автоматически обрабатывать очередь, расписание, обязательные паузы и исключения.

Эта версия восстановлена из исходников `braindiggeruz/telegram-broadcaster`. Прежняя рабочая БД и старый production-хост не найдены и не восстановлены. Локальные проверки не подтверждают работу прежнего сервиса или доставку реальным получателям.

## Запуск на Windows

Нужны Node.js 24, pnpm 10.4.1 и PostgreSQL 17. Для PostgreSQL вне стандартной папки задайте `PG_BIN` с путём к его `bin`.

Ярлык сам устанавливает зависимости, если их ещё нет. Для ручной установки выполните в папке проекта:

```powershell
pnpm install --frozen-lockfile
```

Затем запустите **`Start-TG-Sender.cmd`**. Он создаёт приватную конфигурацию, поднимает отдельный локальный PostgreSQL на порту 54329, применяет миграции, собирает приложение и запускает API вместе с worker. Существующий процесс на порту 3037 сохраняется; повторный запуск ярлыка не заменяет уже работающую версию.

Откройте [http://127.0.0.1:3037](http://127.0.0.1:3037). Пароль владельца лежит только в приватном локальном файле **`.runtime/owner-password.txt`**. `.env`, ключи и `.runtime` не должны попадать в Git, сообщения или скриншоты.

Эквивалентный ручной запуск:

```powershell
pnpm install --frozen-lockfile
pnpm setup:local
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/local-postgres.ps1
pnpm db:migrate
pnpm build
pnpm start
```

`pnpm start` запускает API и отдельный worker через supervisor. Он перезапускает завершившиеся процессы с задержкой. Локальные логи запуска ярлыком находятся в `.runtime/app.log` и `.runtime/app-error.log`. Установщик сохраняет существующий `.env`; его нельзя удалять ради повторного запуска, поскольку там находятся ключи уже зашифрованных данных.

## Рабочий процесс

1. Войдите паролем владельца. Проверьте готовность БД и worker в интерфейсе.
2. Импортируйте CSV/XLSX/JSON, выберите колонку и тип адресата, проверьте предпросмотр и источник согласия. Согласие привязано к выбранному способу отправки; повторный импорт не отменяет отписку.
3. Подготовьте сообщение и запустите **тестовую кампанию**. Черновики сохраняются на сервере. Реальные сообщения по умолчанию выключены: `LIVE_SEND_ENABLED=false`.
4. Для повторяющейся работы создайте утверждённый сценарий расписания или webhook. Источник аудитории может получать разрешённые изменения из CRM через свой защищённый endpoint.
5. Следите за защищённым разделом исключений. Внешние push-уведомления владельцу сейчас не реализованы.

| Исход                  | Что он означает                                                                                                                          |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `accepted`             | Telegram подтвердил принятие сообщения либо владелец явно подтвердил неизвестный исход с доказательством. Это не подтверждение прочтения |
| `dry_run`              | Проверки выполнены без обращения к транспорту отправки                                                                                   |
| `unknown`              | Надёжного результата нет. Автоматического повторения не будет                                                                            |
| `suppressed`           | Получатель исключён: нет допустимого согласия или действует запрет контакта                                                              |
| `stopping` / `stopped` | Остановка запрошена / активная операция завершена и остановка подтверждена                                                               |

При `429`, `FLOOD_WAIT` и `SLOWMODE_WAIT` система сохраняет требуемое ожидание в БД. Антиспам-ограничение или потеря авторизации переводят работу на проверку владельца. Перезапуск не отменяет паузу. Гарантий отсутствия блокировок нет; ротация аккаунтов для обхода запретов не предусмотрена.

## Проверки

```powershell
pnpm check
pnpm test
node scripts/test-db.mjs
pnpm build
```

`pnpm test` запускает обычные тесты; PostgreSQL-тесты требуют `TEST_DATABASE_URL`. `node scripts/test-db.mjs` подставляет локальный `DATABASE_URL`, если отдельный тестовый URL не задан. Используйте локальную тестовую БД: интеграционные проверки создают и удаляют свои случайные схемы, используют синтетические данные и подменённые транспорты. Никаких команд реальной рассылки в этом руководстве нет.

Сохранённые результаты **26 октября 2026, до безопасной паузы**: **109/109 тестов в 16 файлах**, успешные typecheck и production build; браузерный сценарий Chromium — **45/45 проверок без ошибок**, затем **3/3 проверки уточнённого интерфейса** и отдельная проверка времени истории. Зашифрованная копия восстановлена в отдельную временную БД: **30 таблиц, 13 миграций**, сверка успешна, временная БД удалена. Production dependency audit: **0 critical, 0 high, 1 moderate**; оставшийся advisory и границы проверок описаны в [RELEASE_2_RU.md](docs/RELEASE_2_RU.md).

Эти результаты относятся к сохранённой сборке перед паузой. После перезапуска отдельно проверяются готовность приложения и вход владельца; прежние прогоны не подтверждают текущее состояние процессов.

## Подключение владельцем перед будущим пилотом

Владелец вводит свой bot token в защищённом интерфейсе. Для личного аккаунта нужны собственные `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` в приватной конфигурации и вход через код/2FA. Смена отправителя требует повторной проверки разрешений и утверждённых кампаний.

Для Telegram webhook нужен доступный Telegram публичный **HTTPS-адрес**: настройте сертификат и reverse proxy к API, укажите точный HTTPS-origin в `APP_ORIGIN` и сохраните отдельный `TELEGRAM_WEBHOOK_SECRET`. Затем владелец явно подключает webhook в интерфейсе. `/subscribe` включает подписку, `/stop` и `/unsubscribe` прекращают её. Локальный `127.0.0.1` не является публичным адресом для webhook.

До отдельного небольшого пилота оставляйте реальные отправки выключенными. Сначала проверьте собственные доступы, права бота, ожидающую сообщения аудиторию и восстановление резервной копии. Бот не может первым написать произвольному человеку из таблицы. Реальные Telegram-подключения, публичный HTTPS и production-пилот не входят в доказанные локальные результаты.

## Архитектура и восстановление

React → tRPC API → PostgreSQL со снимками кампаний → отдельный worker → Telegram. Очередь, попытки, ограничения, отписки и расписание находятся в БД. Блокировка отправителя действует между процессами. Неизвестные исходы после сбоя сохраняются для проверки, без слепого повторения.

Ежедневная зашифрованная резервная копия и проверка восстановления описаны в [OPERATIONS_RU.md](docs/OPERATIONS_RU.md). Для расшифровки архива нужен `BACKUP_KEY_BASE64`, для сохранённых Telegram credentials — прежний `ENCRYPTION_KEY`. Ключи хранят отдельно от дампа. Копия на том же диске не защищает от потери диска; облачного копирования и автоматического удаления архивов сейчас нет.

Откат выполняется восстановлением **в новую БД** с подходящей версией кода и прежними ключами, при выключенных отправках. Обратных миграций нет; старый код нельзя подключать к новой схеме без проверки совместимости. Подробный порядок — в [описании релиза](docs/RELEASE_2_RU.md#откат).
